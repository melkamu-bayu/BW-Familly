# CLAUDE.md — AssetFlow Mobile

Context for Claude Code (or any agent) working on this project locally.

## What this is

Flutter client for AssetFlow, a business/revenue/expense management system
covering Vehicles, Rental Houses, a Construction Materials Shop, and a
Gold-Mining Project. It talks to a FastAPI backend that lives in a sibling
`assetflow-backend/` project (see that project's own README for backend
setup).

This project was scaffolded and written without ever running `flutter pub
get` or `flutter analyze` against it (it was authored in a sandboxed
environment with no Flutter SDK and no network access to pub.dev). It has
been checked by hand for brace/paren balance, duplicate class/provider
definitions, and import resolution — but **not compiled**. Treat the first
`flutter analyze` run as the real first correctness check, and expect to fix
issues it surfaces.

## First-time setup checklist

Run these in order. Don't skip `flutter create .` — this checkout has no
`android/` or `ios/` platform folders, since those are generated by Flutter
tooling rather than hand-written.

```bash
flutter create .          # scaffolds android/, ios/, etc. -- safe, won't touch lib/ or pubspec.yaml
flutter pub get
flutter analyze           # fix whatever this reports before doing anything else
```

## Building

Two helper scripts do the full build pipeline (create → pub get → analyze →
build) so you don't have to remember the steps or flags:

```bash
./scripts/build_android.sh          # release APK -> build/app/outputs/flutter-apk/app-release.apk
BUILD_MODE=debug ./scripts/build_android.sh   # debug APK instead

./scripts/build_ios.sh              # macOS + Xcode only; unsigned simulator build
./scripts/build_ios.sh --device     # signed build for a real iPhone (needs Xcode signing set up first)
```

`build_ios.sh` will refuse to run (with a clear message) on anything that
isn't macOS — iOS builds require Xcode, which is an Apple platform
restriction with no workaround, not a missing flag.

## Backend connection

The app reads its API base URL from a compile-time define, defaulting to
the Android emulator's host-loopback address:

```bash
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000/api/v1   # Android emulator (default)
flutter run --dart-define=API_BASE_URL=http://localhost:8000/api/v1  # iOS simulator
flutter run --dart-define=API_BASE_URL=http://192.168.1.X:8000/api/v1 # physical device on same LAN
```

The backend needs to actually be running for anything past the login screen
to work — see `../assetflow-backend/README.md`. Seeded login:
`admin@assetflow.local` / `ChangeMe123!`.

## Project structure

```
lib/
  core/        config, api_client (JWT + refresh), secure_storage, local_db,
               outbox_repository, sync_service, theme, rate_limit-adjacent bits
  models/      Dart models mirroring the backend's Pydantic schemas
  state/       Riverpod providers (auth_provider, data_providers, lock_provider)
  screens/     one folder per feature area
  widgets/     nav_shell, idle_lock_gate, summary_card
  router.dart  go_router config with auth-based redirects
  main.dart    entrypoint
```

Full inventory of what's implemented vs. not yet built is in `README.md`
under "What's implemented" / "What's next" — check there before assuming a
feature is or isn't wired up.

## Known risk areas to check first with `flutter analyze`

These are the parts most likely to have drifted or have a typo, since they
were the most recently added and involved the most manual cross-referencing
between the mobile models and the backend's Pydantic schemas:

- `lib/models/models.dart` — every model's `fromJson` needs to match the
  backend's actual JSON keys exactly (snake_case in JSON → camelCase in
  Dart). Cross-check against `assetflow-backend/app/schemas/*.py` if a
  runtime `null` or type error shows up here.
- `lib/state/data_providers.dart` — every provider's endpoint path needs to
  match a real backend route. Cross-check against
  `assetflow-backend/app/api/v1/*.py`.
- `lib/widgets/idle_lock_gate.dart` + `lib/state/lock_provider.dart` — the
  idle-lock feature was refactored partway through development (from local
  widget state to a shared provider); double check there's no leftover
  reference to the old approach.

## Conventions

- State management: Riverpod (`flutter_riverpod`), not Provider or Bloc.
- Navigation: `go_router`, not Navigator 2.0 hand-rolled or auto_route.
- Every list screen follows the same shape: a `FutureProvider` in
  `data_providers.dart` + a `ConsumerWidget` with `.when(loading, error,
  data)`. Follow this pattern for any new screen rather than introducing a
  different one.
- Offline writes (currently revenue/expense only) go through
  `OutboxRepository.instance.enqueue(...)`, never a direct `dio.post(...)`
  call — that's what makes them survive being offline. See
  `screens/transactions/add_transaction_sheet.dart` for the reference
  implementation.
